# Architecture decision: HAPI, named PACs and harness adapters

## Decision and status

HAPI remains the user-facing hub and session-control surface. OpenCode is the first source harness for integration; the bridge must accommodate multiple source and destination harnesses, including a future Oh My Pi (OMP) evaluation. Named PACs identify independently authenticated agent runtimes and their individual model catalogs. The intended outcome and acceptance tests are in [ACCEPTANCE.md](ACCEPTANCE.md).

HAPI requires a real harness on the source machine to create a session. The required UX is to select that machine and a supported harness, then choose `PAC_<name>/<model>` in its model picker. That choice must route the session to the authenticated Claude Code on the selected PAC while keeping tools in the intended workspace; no source-side Claude login is required. Merely displaying a model entry without routing its agent session and complete functionality does not satisfy this decision. HAPI's existing OpenCode integration is the first candidate for this user workflow; OMP remains a parallel adapter candidate until its HAPI session and model-picker integration are verified.

In the inspected HAPI source, the Pi integration starts Pi with `--mode rpc`; OMP's separate `acp` command is not a drop-in proof of compatibility with that path. The actual installed HAPI version and OMP RPC compatibility must be tested before registering OMP as a HAPI harness. HAPI's OpenCode integration and model-picker behavior must likewise be verified end to end rather than inferred from their presence.

This is a design decision and an initial ACP stdio adapter, not a working remote integration. The existing bridge still relies on a shared filesystem for native Claude file tools. It does not meet the acceptance criteria.

## Boundaries

- The source adapter represents the originating harness and workspace; the destination adapter represents the selected PAC runtime. Adapters must preserve bidirectional requests, events, results, permissions and lifecycle without conflating the two sides.
- The PAC identity and selected model are bound to each session. Discovery and authorization must not expose other users' PACs. A reconnect must not silently reroute a session or replay an operation with an uncertain outcome.
- HAPI is the control and presentation layer. Using two HAPI sessions as a transparent data plane is not assumed: ordinary chat messages or session histories do not, by themselves, preserve bidirectional tool calls, cancellation, task identities, model selection and approval semantics. A HAPI transport can be used only after its actual API demonstrates those properties. Until then, the agent protocol needs a separate authenticated bidirectional transport; HAPI can present and control the resulting sessions.
- OMP's ACP mode exposes an agent to an ACP client and can delegate certain tools to that client. This does not automatically make OMP a client for a remote Claude Code agent, turn a Claude Code session into an LLM model endpoint, or guarantee parity for background tasks and subagents. Those directions require explicit adapters and tests. Do not export or reuse Claude subscription credentials as a model API key.
- Tool calls must execute in the intended workspace with no shared filesystem. The bridge must preserve all supported operations, including model selection, native and MCP tools, background jobs, nested subagents, progress, permissions and cancellation. Unsupported capabilities block a full-parity claim rather than being silently dropped.
- The destination harness must match or exceed the required Claude Code feature set. Hooks, skills, custom commands, instructions and extensions must preserve their execution side and semantics, not merely be replaced with similarly named features. An evidence-backed feature matrix and end-to-end tests determine eligibility; OMP is the first candidate, not a proven match.

## Initial adapter

`node adapters/acp-stdio.mjs omp` starts `omp acp` and transparently passes stdin and stdout; set `PAC_OMP_BIN` to an executable path when `omp` is not on PATH. `node adapters/acp-stdio.mjs <executable> [arguments...]` permits other ACP agents. The adapter uses no shell and forwards stderr separately, keeping the JSON-RPC stream intact. This is a local process boundary only: it does not implement remote transport, registry, authentication, a HAPI connection or an OMP-to-Claude adapter.

`src/pac-catalog.mjs` is an in-memory selection primitive for named PACs and their models. It requires an explicit set of authorized PAC IDs from its caller; it does not authenticate clients, provide persistence, discover runtimes or expose models to HAPI. Names are case-insensitively unique, offline entries cannot be selected, and a resolution returns the stable PAC identity separately from its display name.

`src/acp-workspace.mjs` implements local, session-bound ACP text read/write operations with bounded sizes and path checks. An experimental test router connects it to OpenCode and HAPI; this is not a production integration. Its path checks are not an OS sandbox: a hostile local process could race filesystem changes, so the surrounding deployment must enforce operating-system isolation and authorization independently. Binary files, search, edits, terminals, hooks and background task semantics are not implemented by this module itself.

Next milestones are production-grade source and controller adapters, authorized named PAC discovery, complete tool and lifecycle routing, and verification against the complete acceptance matrix.

The experimental ACP relay can be enabled on the existing server with `PAC_ACP_RELAY_ENABLED=1`. It relays a separate byte stream for each session and checks the existing scoped brain and client tokens, but does not itself implement model discovery, routing in OpenCode or workspace tool interception. `adapters/pac-acp-agent.mjs` and `adapters/pac-acp-source.mjs` start the corresponding process and stdio endpoints with tokens read from files. Remote clients require `wss://`; production must terminate TLS at a trusted proxy and protect the server's private HTTP listener. The transport reports disconnects and does not automatically retry requests. An isolated cross-host test with a temporary TLS relay, real HAPI runner, OpenCode, Claude ACP and authenticated Claude Code has demonstrated model discovery before session creation, selection in the runner spawn request, confirmation of the selected model in the new session, source-side Read/Write/Edit and foreground Bash, and a background subagent reading a source-only fixture. Two named endpoints were tested on the same controller and account, not on independently authenticated controllers. These fixtures are prototypes and do not establish full functional parity or production readiness.

An agent can opt into registration reconnect with `PAC_AGENT_RECONNECT=1`. A lost registration closes its active session processes before registering again; interrupted requests are not replayed and require explicit recovery. The adapter rereads its token file for each registration attempt. An automated relay test interrupts a call after a real side effect, verifies an unknown outcome, and confirms that reconnecting did not repeat that side effect. This primitive does not restore running work or establish production availability guarantees.

The installed Claude ACP adapter version 0.88.0 and the inspected upstream version expose file-related ACP client methods but do not automatically replace all Claude Code native filesystem tools with those methods. Advertising ACP filesystem capability alone therefore does not route native Read/Edit/Glob/Grep to the client. The workspace handler must not be presented as a solution to this gap; resolve and verify native-tool interception before making a PAC model selectable in a real workspace session.

An isolated proof uses SDK-hosted MCP tools and aliases to route Read, Write, Edit, a limited Glob/Grep subset, and Bash to the source workspace while leaving selected native tools available. Search uses source-side ripgrep with bounded output and time, and explicitly rejects invalid paths and search options. Foreground Bash approval and denial, and workspace write denial, have been exercised through HAPI; denied operations did not modify the fixture. A source background shell command was shown running in HAPI and its output was retrieved through an experimental MCP task tool. A background subagent has used the source Read tool; its active and completed status was observed through an experimental patched HAPI client and hub. A completed session was archived and resumed through the HAPI runner with its original PAC, model, conversation context, and a subsequent source-side write. A separate experimental hook path ran a project PreToolUse denial and a PostToolUse command on the source machine. This demonstrates a candidate integration, not native-tool equivalence: several native tools and project settings are disabled, Edit is a non-atomic read-then-write, background shell task naming and recovery are not native-equivalent, search lacks various native options, and skills, most hook forms and scopes, other approval paths, recovery of active work, and full error semantics remain unverified. SDK hooks observe the MCP-prefixed tool name in alias mode; the experimental project hook path maps the tested built-in tool names back before dispatch. It must not be enabled as a full-parity solution.

The search proof requires ripgrep on the source machine (`PAC_SOURCE_RG` can specify its executable). It does not follow directory symlinks and rejects explicitly selected paths resolving outside the workspace. These path checks do not prevent filesystem races or replace operating-system permissions. The search capability is experimental and is not a claim that all Claude Code Glob/Grep options are supported.

The experimental Read alias can return bounded PNG, JPEG, GIF and WebP data as an image tool result after checking its signature; a small PNG was recognized by the remote model in a cross-host test. Only PNG has end-to-end evidence. PDF, other binary content, large payloads and native Read's complete behavior remain unsupported or unverified. Image bytes travel as a tool result, not through a shared filesystem.

The experimental project hook dispatcher supports synchronous command hooks for tested PreToolUse, PostToolUse and PostToolUseFailure events from project and local project settings. A cross-host failure test distinguished an executed tool failure from earlier pre-execution denials. Distinct matching hooks run concurrently and identical handlers are deduplicated; merging multiple outputs is restricted to simple PreToolUse allow, ask and deny decisions. Other combinations fail closed. It rejects unsupported hook events, handlers and settings instead of silently skipping them. It does not yet implement user or managed settings, plugins, skill hooks, asynchronous hooks, other lifecycle events, or complete native hook precedence and error behavior. The source workspace must be trusted before enabling its hooks.

An opt-in shell output pump forwards bounded running-output snapshots as explicitly tagged ACP tool updates. A patched HAPI backend converts them into running tool progress, and an isolated cross-host test observed the first output before completion for a root command and a child-scoped subagent command. An HAPI abort also stopped a running source command before a delayed side effect. Isolated HAPI tests cancelled pending foreground and background command approvals and a pending write approval, rejected late approvals, and observed no side effects. A concurrent approval and cancellation after execution starts can still leave the outcome uncertain. This does not establish browser rendering, complete stdout/stderr fidelity, or recovery of running processes after disconnect.

The patched HAPI exposes experimental, session-scoped PAC task controls. They route a stop request to the selected PAC and reject task identities not belonging to that session. Acknowledgement means that stop was requested, not necessarily that the task has stopped; the UI keeps the task visible until a lifecycle update removes it. A browser test on each of two Windows source hosts created an OpenCode session with a named PAC model, sent a prompt and stopped a running native subagent. These were isolated installations, not deployment into the user's HAPI.

The isolated HAPI proof also exercised a simple project skill and source project instructions. The skill adapter accepts only a restricted frontmatter and substitution subset. The instruction adapter supports bounded workspace imports in unit tests and explicitly rejects external imports; it does not implement their approval flow or complete Markdown and scoped-rule semantics. Neither adapter represents complete Claude Code equivalence. On Windows, source shell commands and hooks are started inside a kill-on-close Job Object, so cancellation also terminates descendants that Git Bash has reparented. This containment does not replace workspace security controls and requires a Windows version supporting process creation with a job-list attribute.

An opt-in experimental `AskUserQuestion` MCP alias forwards question data to HAPI and returns indexed answers to the remote runtime. A cross-host test submitted one free-text answer and a multi-select answer through HAPI's API in automatic-approval mode, verified the originating root tool identity, denied another question, aborted a pending question and rejected its late approval, and answered a subagent question with a child-scoped identity. HAPI reducer tests cover pending and completed root question cards. This is not evidence of complete native question-tool equivalence: browser interaction, nested-agent card association, other cancellation paths and concurrent questions remain to be verified. When a subagent is active and the question's owner cannot be determined, the prototype fails closed instead of silently treating it as a root question.

The experimental router can persist the source session ID, stable PAC ID, remote session ID, selected model, and source workspace under `PAC_SESSION_DIR`; credentials are not included. A resumed session must use the same workspace and PAC, and a missing or invalid binding fails closed instead of silently starting a new session. The directory still contains session identifiers and workspace paths and must be protected by operating-system permissions. The current proof restores a completed conversation, not running background tasks or uncertain operations after a transport failure.

In the tested HAPI OpenCode integration, an in-session model change is applied to the backend when the next turn starts, not necessarily when the model-selection request returns. A cross-host test switched from Sonnet to Opus and back, and the Claude usage events identified an Opus model and then a Sonnet model. The PAC adapter requires the remote session to confirm the model before sending the turn; this does not establish support for every model variant or for mid-turn switching.

The automated primitive suite has run natively on Windows and Linux without Docker. This is not a cross-platform end-to-end acceptance result: the authenticated Claude/HAPI proof has used Windows hosts, and macOS and Linux harness-to-harness operation remain unverified.

Run the local primitive suite with `node --test "test/*.test.mjs"` after installing the package dependencies and ripgrep. Some environment-specific tests are skipped unless their optional prerequisites are supplied; skips are not passing evidence for those environments. The HAPI runner and hub changes have separate tests in the HAPI checkout and are not installed into an existing runner by this command.

`src/pac-session.mjs` provides ACP initialization, per-session model discovery and confirmed selection, and `src/acp-peer.mjs` handles bidirectional JSON-RPC without automatic retry. They are integration primitives, not a HAPI or OpenCode adapter. Model changes are rejected unless the remote session reports the requested selection.
