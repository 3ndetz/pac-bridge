# Skills and hooks

PAC Bridge discovers supported file-backed skills on the source machine in project `.opencode/skill`, `.opencode/skills`, `.agents/skills`, and `.claude/skills`, as well as the corresponding supported user directories, including nested skill directories up to six levels deep. Project directories are searched from the working directory up to the nearest Git root, with the nearer definition taking precedence; outside Git, the search stops before the user's home directory. A supported skill has simple `name` and `description` frontmatter; string `license` and `compatibility` fields are also accepted. When invoked, its own resource files can be read from the source machine. The bridge also queries the installed OpenCode for built-in skills, with a time and output limit, and passes their content without granting a filesystem root. If that query fails, a warning is written to the runner log and file-backed skills remain available. Other metadata, dynamic substitutions, custom skill paths, and native OpenCode plugin hooks are not yet generally supported.

The bridge supports source project command hooks in `.claude/settings.json` and `.claude/settings.local.json` for `PreToolUse`, `PostToolUse`, and `PostToolUseFailure`. Hooks run on the source machine; a pre-tool denial prevents the tool from running. Security-relevant configuration the bridge cannot enforce is rejected instead of being silently ignored. Other hook events and OpenCode plugin APIs are not complete. See [the experiment documentation](../OPENCODE-EXPERIMENT.md) for the exact constraints.

On the existing Windows HAPI runner, real-Claude checks have exercised a project OpenCode skill and its resource, a pre-tool denial, a successful post-tool hook, and a post-tool failure hook. These are scenario-specific results, not proof that every installed skill, plugin, event, or platform is supported. The complete matrix is tracked in [RELIABILITY-CHECKLIST.md](../RELIABILITY-CHECKLIST.md).

The experimental OpenCode provider path was also checked with an unmodified HAPI 0.34.4 client in the existing TS-1CDEV hub: the project skill resource, the three hook scenarios, an explicit approval of a test file write, and non-disclosure of a denied test file all passed. Separate real-Claude provider tests on the first machine confirmed invocation of a nested global `docx` skill and the built-in `customize-opencode` skill. The client was a separate process and the `/workflow/4/` hub uses the corporate baseline; the `/workflow/1/` hub and shared UI still include PAC-specific changes. Individual skills and other hooks or plugins require their own verification.

An optional source-side completion notification is documented separately in [telegram-notifications.md](telegram-notifications.md). It is a bridge completion callback; it does not claim general compatibility with OpenCode plugin hooks.
