# Skills and hooks

PAC Bridge discovers supported file-backed skills on the source machine in project `.opencode/skill`, `.opencode/skills`, `.agents/skills`, and `.claude/skills`, as well as the corresponding supported user directories, including nested skill directories up to six levels deep. Project directories are searched from the working directory up to the nearest Git root, with the nearer definition taking precedence; outside Git, the search stops before the user's home directory. A supported skill has simple `name` and `description` frontmatter; string `license` and `compatibility` fields and a string-to-string `metadata` map are also accepted. In line with OpenCode V1, the bridge does not interpret the metadata. When invoked, its own resource files can be read from the source machine. The bridge also queries the installed OpenCode for built-in skills, with a time and output limit, and passes their content without granting a filesystem root. If that query fails, a warning is written to the runner log and file-backed skills remain available. Other frontmatter, dynamic substitutions, custom skill paths, and native OpenCode plugin hooks are not yet generally supported.

The bridge supports source project command hooks in `.claude/settings.json` and `.claude/settings.local.json` for `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, and `UserPromptSubmit`. Hooks run on the source machine; a pre-tool denial prevents the tool from running. For `UserPromptSubmit`, plain text adds context and exit code 2 blocks the prompt; unsupported matchers are rejected. This event requires matching source and controller support: a configured hook blocks the turn if the controller does not confirm support. The hook receives the original single-text-block prompt; multimodal or multi-block input is rejected while this hook is configured. Synthetic tests verify prompt blocking, context delivery, source routing and mixed-version handling. A real Claude check through the first existing HAPI runner also blocked a prompt and delivered hook context after the provider and controller were updated; the second profile remains unverified for this event. Security-relevant project configuration the bridge cannot enforce is rejected instead of being silently ignored. PAC models can still be listed in a workspace with an unsupported OpenCode plugin; a PAC turn is stopped with an explanation until that plugin is supported or removed. Supported command hooks from the user's global `.claude/settings.json` are combined with project and local hooks; the global file is read once even when the workspace is home. A small explicit preference subset is accepted, and validated effort, disabled automatic model switching and the nonessential-traffic setting can be supplied to the controller. Other global preferences, environment variables and proxy settings fail explicitly. This does not enable the synthetic-only Stop lifecycle route. Other hook events and OpenCode plugin APIs are not complete. See [the experiment documentation](../OPENCODE-EXPERIMENT.md) for the exact constraints.

On the existing Windows HAPI runner, real-Claude checks have exercised a project OpenCode skill and its resource, a pre-tool denial, a successful post-tool hook, and a post-tool failure hook. These are scenario-specific results, not proof that every installed skill, plugin, event, or platform is supported. The complete matrix is tracked in [RELIABILITY-CHECKLIST.md](../RELIABILITY-CHECKLIST.md).

The HAPI model probe has its own 30-second limit. A cold native OpenCode startup with a project plugin was observed to exceed that limit; a later warm retry returned native models. The bridge allows up to 27 seconds for native initialization and model listing together, but cannot extend HAPI's limit without changing HAPI. A timeout can therefore temporarily prevent even native models from appearing.

The experimental OpenCode provider path was also checked with an unmodified HAPI 0.34.4 client in the existing second machine hub: the project skill resource, the three hook scenarios, an explicit approval of a test file write, and non-disclosure of a denied test file all passed. Separate real-Claude provider tests on the first machine confirmed invocation of a nested global `docx` skill and the built-in `customize-opencode` skill. The client was a separate process and the second hub uses the corporate baseline; the first hub and shared UI still include PAC-specific changes. Individual skills and other hooks or plugins require their own verification.

An optional source-side completion notification is documented separately in [telegram-notifications.md](telegram-notifications.md). It is a bridge completion callback; it does not claim general compatibility with OpenCode plugin hooks.


## Private Windows Stop transcript groundwork

The synthetic lifecycle route (`PAC_TEST_SYNTHETIC_LIFECYCLE=1`) can now exercise Stop block/continue and resume on Windows as well as Linux. This flag is still required; global Stop hooks and installed-runtime compatibility are not enabled by these checks.

On Windows, snapshot reads require a local NTFS path, retained non-reparse directory handles, a single-link regular file of at most 1 MiB, and a read handle that excludes concurrent writes and deletion. The file owner must be the current user or the current token default owner; the latter is the [SID Windows applies to newly created objects](https://learn.microsoft.com/en-us/dotnet/api/system.security.principal.windowsidentity.owner?view=netframework-4.8.1). ACL grants may target only the current user, SYSTEM or Administrators. Other grants are rejected. An existing broadly inherited SDK profile is not silently repaired or accepted. Synthetic SDK tests provision a private disposable profile before creating history.

The source-side callback receives an ephemeral user-only transcript created atomically inside a protected directory. Its retained handles exclude file replacement and directory renaming. Delete-on-close removes the file on host termination, and loss of the parent owner pipe terminates the contained helper job. Normal completion also removes the empty directory. A hard crash can leave an empty directory or compiler scratch data; these require separately verified ownership before removal. The helper does not sandbox code running under the same Windows account.

Focused tests cover encoding/size bounds, default-token ownership, broad ACL rejection, hard links, junction ancestors, concurrent writer rejection, keeper write/rename rejection, callback failure, real source hook execution and parent loss. The parent-loss fixture confirms its enclosing Job has zero processes before removing its synthetic profile. The fake-model controller scenario covers Stop block/continue and resumed history without paid calls or real MCP/plugin discovery.
