# Updating an existing PAC Bridge

`git pull` updates the source checkout. It does not replace the staged provider, running controller, relay or already-open chat processes. Current main adds mandatory authenticated source/session ownership. Do not activate it over an existing installation until its legacy bindings and coordinated relay/controller transition are prepared. The currently installed revision must be checked independently of Git HEAD.

1. Verify the intended full commit and its acceptance evidence. Record the current installed revision, selector and wrapper. Preserve private connection files, the existing HAPI profile/identity and session bindings, controller transcripts and ownership directory, and installer-generated verified backups. Keep these outside Git and restrict them to the operating account. Check native OpenCode configuration/plugin compatibility before activation; a passing synthetic suite does not establish compatibility with a real profile. The current source adapter excludes local Claude configuration; do not change local Claude settings or proxy entries to repair OpenCode startup. See [the source harness contract](skills-hooks.md).
2. Prepare distinct source trust domains and credential-rotation mappings in the private relay authorization file. Follow [session authorization](session-authorization.md). A shared token is a shared identity. Prepare and review the legacy ownership manifest from trusted source records and backups; use its read-only migration plan before applying. No legacy session is adopted automatically.
3. Schedule the relay/controller change when their affected chats have drained. The relay must provide authenticated principals before the new agent can start controllers. A new agent refuses an older relay. Preserve existing credentials and source identity mappings during the transition. A relay restart interrupts established channels; do not use active conversations as a migration test.
4. Synchronize the clean checkout with `git fetch` and `git pull --rebase`. On Windows, source-side staging uses `windows/Install-ProviderMode.ps1 -KitPath <existing-kit> -Activate -NamedProviders` after the preceding checks. Review the separate `-LegacyMigration` requirement for the specific profile. The installer is not a substitute for controller ownership migration. New dispatch-enabled chats use the selected staged revision; existing chats retain their original processes. Older fixed wrappers require their documented migration or a normal runner restart. See [Windows setup](windows-setup.md).
5. Linux staging/update and rollback remain under verification; [POSIX setup](posix-setup.md) describes the current restrictions. Retain unresolved stage/lock state after SIGKILL for ownership review. Do not remove locks merely because an installer is no longer visible. macOS acceptance is deferred.
6. Verify discovery and a new chat on the existing hub/machine, tools, permissions, hooks, compaction and recall. Resume a migrated test session as its intended source, and verify a different source is denied. Check restart and concurrent sessions. Record the actual installed SHA and observed results before marking deployment complete. Model-backed checks consume quota and remain explicit test operations.

For rollback, stop admitting new work to the affected revision, drain/close its owned processes, and restore the verified previous selector/wrapper through the documented profile-specific procedure. Restore a matched set of source bindings, controller transcripts and private identity configuration from backups when those were changed. Do not delete ownership records to force a resume or undo a conflict. A source checkout reset alone does not roll back a running or staged installation. Existing private credentials remain in their approved secret store.

This is the coordinated update procedure and a record of current limitations. Automated installed-runtime update/rollback acceptance is still outstanding; no production migration was performed by the synthetic migration tests.
